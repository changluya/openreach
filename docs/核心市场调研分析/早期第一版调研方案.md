# 给 Agent 提供 Web 能力：早期调研与技术决策

## 1. 决策结果

第一阶段基础 Web 能力最终收敛为三个原语：

```text
search(query)        -> 找网页
image-search(query)  -> 文搜图
read(url)            -> 读网页
```

基础层不负责：

```text
LLM Summary
Deep Research
Citation Generation
Query Planner
```

这些属于上层 Agent/Research Orchestration。

---

# 2. 为什么最初是 Search + Read，后来增加 Image Search？

最初最小闭环：

```text
search -> URL -> read
```

已经能解决普通联网问答。

但真实 Agent 场景还会出现：

```text
找产品图
找人物/地点参考图
文章配图
视觉资料收集
图文 Research
```

图片结果的数据结构明显区别于网页结果：

```text
imageUrl
thumbnailUrl
sourcePageUrl
width/height
license
```

所以 Image Search 应成为第三个基础原语，而不是塞进普通 Search DTO。

---

# 3. Search 选型

| 方案 | 优点 | 不足 | 决策 |
|---|---|---|---|
| DDGS | 极快 PoC | Python；上游变化；生产稳定性有限 | 非主链路 |
| SearXNG | 多 Engine、成熟 | 需要额外服务 | 后续生产候选 |
| 多国内/可用 HTML Provider | 单 Java、0 API Fee | 页面会变化、无 SLA | **V1** |
| Serper | Google SERP 稳定、结构化 | 付费 | V2 Premium |
| 自研 Google 抓取集群 | 可控 | 极重、反爬/合规/维护 | 不选 |

V1 普通 Search：

```text
Bing CN -> Baidu -> Sogou -> 360 -> DuckDuckGo
```

---

# 4. Image Search 选型

调研重点：

```text
是否无需 API Key
国内可用性
原图 URL
缩略图
来源页面
尺寸/格式
License
维护复杂度
```

初版选：

```text
Bing Images
Baidu Images
Sogou Images
Openverse
```

原因：

- Bing/Baidu/Sogou 提供通用图片搜索覆盖；
- 百度/搜狗对中文与国内网络更有意义；
- Openverse 是正式 API，可补充 License-aware 场景；
- 这些实现路径均有公开成熟项目/官方 API 可交叉验证；
- 不为了凑数量强行接入未充分验证的图片渠道。

---

# 5. 为什么仍然不做账号池 + 代理池？

如果为了对标商业 SERP 走：

```text
大量账号
Cookie Pool
住宅 Proxy Pool
Captcha
Fingerprint
Block Detection
```

项目会从 OpenReach 变成：

```text
Anti-bot SERP Scraping Platform
```

长期需要维护：

```text
IP reputation
TLS fingerprint
Cookie/session
页面实验
DOM 变化
CAPTCHA
Geo
请求节奏
```

账号并不能解决这些问题，代理也不是零成本。

此外 Serper Terms 当前明确禁止：

```text
同时注册多个账号
绕过 API Key / Account 限制
```

因此商业化阶段正确方案是：

```text
免费 Provider 默认
        ↓
Quality Gate
        ↓
必要时 Serper Premium
```

而不是账号池。

# 6. Read 选型

| 方案 | 优点 | 不足 | 决策 |
|---|---|---|---|
| JDK HttpClient + Jsoup | Java、轻、0 API Fee | 不执行 JS | **V1 默认** |
| Playwright Java | SPA/JS | CPU/内存/延迟 | V1.5 fallback |
| Crawl4AI | AI Crawl 能力强 | Python sidecar | 后续 Provider |
| Firecrawl | 商业成熟 | API 成本 | Premium Reader |

V1 Read：

```text
SafeHttpFetcher
 -> UrlSafetyGuard
 -> Jsoup
 -> Content Scoring
```

---

# 7. “0 成本”的准确含义

当前所谓 0 成本是：

> **无第三方 Search / Image Search / Read SaaS API 调用费。**

仍然存在：

```text
本机/服务器 CPU
内存
公网带宽
开发维护
```

同时免费上游不提供 SLA。

---

# 8. 免费方案和商业方案的边界

免费 Provider 适合：

```text
内部 Agent
PoC
普通信息检索
低~中频使用
Search -> Read
```

Serper 类商业 Provider 适合：

```text
稳定 Google SERP
精确 Geo
Places/Maps/Shopping
Google 排名一致性
高 QPS
低维护成本
```

因此目标不是“永远不用商业 API”，而是：

> **在 Provider SPI 已经稳定的前提下，让商业 API 成为按需增强能力。**

---

# 9. 最终架构决策

```text
                       Agent
                         │
        ┌────────────────┼────────────────┐
        │                │                │
     search         image-search         read
        │                │                │
 SearchProvider   ImageSearchProvider   PageReader
        │                │                │
 Free/Premium      Free/Premium       Jsoup/Browser
```

第一版优先：

```text
接口稳定
本地可跑
零 API Fee
国内可用性
单测覆盖
```

以后再增强：

```text
SearXNG
Serper
Playwright
Research / Citation
```

---

# 10. 一句话结论

> **先建设可替换的 Web 原语，不去建设搜索引擎反爬基础设施；免费 Provider 用于覆盖普通需求，商业 Provider 用于购买稳定性和高阶 SERP 能力。**
