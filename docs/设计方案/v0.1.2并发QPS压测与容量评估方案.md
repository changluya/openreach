# v0.1.2 并发 QPS 压测与容量评估方案

## 1. 目标

OpenReach 的 Search / Image Search / Read 都包含外部 HTTP 访问。如果直接对真实搜索引擎做压测，结果会混入：

- 搜索 Provider 自身响应耗时；
- 目标站点 403 / 429 / Bot Challenge；
- 出口 IP / ASN 信誉；
- 网络 RTT、DNS、TLS；
- Provider 限流和临时波动。

因此 v0.1.2 将性能验证拆为两层：

1. **OpenReach HTTP 应用基准**：真实 Spring Boot HTTP 链路 + 内存 Provider，测应用自身 QPS。
2. **真实上游压测**：调用实际运行中的 `/api/web/search`，测最终业务吞吐和上游承压情况。

不能把第二层测到的低 QPS 直接认定为 OpenReach Java 服务性能不足。

---

## 2. 新增 JUnit 并发基准

测试文件：

```text
src/test/java/io/github/changlu/openreach/performance/OpenReachApiQpsBenchmarkTest.java
```

测试覆盖完整路径：

```text
JDK HttpClient
  -> Tomcat random port
  -> RequestTraceFilter
  -> AttackSurfaceFilter
  -> Jackson JSON Deserialize
  -> WebCapabilityController
  -> SearchService
  -> benchmark SearchProvider
  -> SearchResponse
  -> Jackson JSON Serialize
  -> HTTP Response
```

其中 benchmark Provider 只返回固定内存数据，不进行公网访问。

这意味着测试会覆盖 OpenReach 的：

- HTTP Server；
- 请求体读取与安全过滤；
- Trace ID 创建；
- Logback API / Upstream 日志；
- Controller；
- 参数校验和 JSON；
- SearchService Provider 调度；
- 响应序列化。

### 为什么默认不进入普通单测

性能指标高度依赖 CPU、磁盘、JDK、容器资源和宿主机负载。如果把 QPS 阈值直接加入普通 `mvn test`，容易产生 CI 假失败。

因此该测试使用：

```text
-Dopenreach.qps.enabled=true
```

显式开启。普通功能测试仍保持稳定。

## 3. 一键执行

```bash
./bin/quick/qps-unit-test.sh
```

默认：

```text
REQUESTS_PER_LEVEL=500
WARMUP_REQUESTS=50
CONCURRENCY_LEVELS=1,4,8,16,32
PROVIDER_DELAY_MS=0
QPS_API_LOG_LEVEL=INFO
QPS_UPSTREAM_LOG_LEVEL=INFO
```

建议正式容量测试：

```bash
REQUESTS_PER_LEVEL=5000 \
WARMUP_REQUESTS=500 \
CONCURRENCY_LEVELS=1,4,8,16,32,64,128 \
./bin/quick/qps-unit-test.sh
```

模拟上游单次耗时 20ms，观察 OpenReach 并发调度能力：

```bash
PROVIDER_DELAY_MS=20 \
REQUESTS_PER_LEVEL=2000 \
CONCURRENCY_LEVELS=1,8,16,32,64 \
./bin/quick/qps-unit-test.sh
```

如果希望后续作为指定机器上的性能回归门槛，可选设置峰值 QPS 下限：

```bash
MIN_PEAK_QPS=500 \
REQUESTS_PER_LEVEL=3000 \
CONCURRENCY_LEVELS=8,16,32,64 \
./bin/quick/qps-unit-test.sh
```

`MIN_PEAK_QPS=0`（默认）只生成报告，不用硬件相关性能阈值阻断测试。

## 4. 指标

测试输出：

| 指标 | 含义 |
|---|---|
| Concurrency | 并发 Worker 数 |
| Requests | 当前档位请求总数 |
| Success / Fail | 成功和失败请求数 |
| Duration | 完成当前档位所有请求的墙钟时间 |
| QPS | `总请求数 / 总耗时秒数` |
| Avg | 单请求平均延迟 |
| P50 | 50% 请求不超过该延迟 |
| P95 | 95% 请求不超过该延迟 |
| P99 | 99% 请求不超过该延迟 |
| Max | 最大请求延迟 |
| HTTP status | 状态码分布 |

结果自动保存：

```text
target/qps/openreach-qps-report.md
target/qps/openreach-qps-report.csv
```

建议容量判断优先看：

```text
QPS + P95 + P99 + 错误率
```

而不是只看最高 QPS。

## 5. 日志对 QPS 的影响

当前生产模式每次 API 会生成 Trace/API 日志，Search 还会生成 Provider 中间过程日志，并落盘到 Logback RollingFileAppender。

这部分属于真实生产成本，因此 QPS 基准默认保持：

```text
OPENREACH.API=INFO
OPENREACH.UPSTREAM=INFO
```

为了判断日志 I/O 成本，可以额外跑一组：

```bash
QPS_API_LOG_LEVEL=WARN \
QPS_UPSTREAM_LOG_LEVEL=WARN \
./bin/quick/qps-unit-test.sh
```

两组结果差值可以近似反映当前高频 INFO 日志对吞吐的影响。

如果后续 QPS 较大，可进一步考虑：

1. Logback AsyncAppender；
2. 高频成功日志采样；
3. ERROR/WARN 全量、成功 Provider 日志按比例采样；
4. 独立日志采集 Agent；
5. 避免业务线程同步等待慢磁盘。

但在没有压测数据前，不建议提前把全部日志异步化，避免增加丢日志和排障复杂度。

## 6. 真实上游压测

服务启动后：

```bash
BASE_URL=http://127.0.0.1:8080 \
TOTAL_REQUESTS=50 \
CONCURRENCY=5 \
./bin/quick/qps-test.sh
```

脚本输出：

```text
success / failed
successRate
throughputQps   # 所有 HTTP 请求吞吐，包含失败响应
successfulQps   # 仅 2xx 成功请求吞吐
avg
P50 / P95 / P99 / max
HTTP status 分布
```

真实压测客户端按 Worker 复用 HTTP keep-alive 连接，减少每次请求都重新 TCP 建连造成的客户端侧失真。

报告：

```text
target/qps/openreach-real-qps-report.json
```

失败时额外生成：

```text
target/qps/openreach-real-qps-failures.json
```

其中保留失败响应的 `traceId`，可以立即关联：

```bash
OPENREACH_LOG_DIR=/data/openreach/logs \
./bin/quick/logs.sh trace <traceId>
```

## 7. 关于真实 Provider QPS 的判断

如果应用基准 QPS 很高，但真实上游 QPS 很低，应优先查看：

```text
openreach-upstream.log
```

按失败类型统计：

- `HTTP_403`
- `HTTP_429`
- `BOT_CHALLENGE`
- `TIMEOUT`
- `PARSE_EMPTY`
- `IO_ERROR`

典型判断：

### A. P95 很高，但没有 403/429

更可能是上游网络 / Provider 响应慢。

### B. 并发越高，403 / Bot Challenge 越多

说明第三方站点反自动化策略开始生效，此时不应该继续简单提高线程数。

### C. 出现大量 429 / Retry-After

应增加 Provider 级限流、退避和 Cooldown，而不是继续加并发。

### D. 应用基准 QPS 低、CPU 不高、日志磁盘繁忙

重点评估 Logback 同步文件 I/O 和 AsyncAppender。

### E. 应用基准 QPS 随并发提升后很快停止增长且 CPU 满载

重点做 CPU Profile、JSON、日志格式化、对象分配和 Tomcat 线程参数分析。

## 8. 后续建议容量测试矩阵

建议以后每次重大版本至少保留以下结果：

| 场景 | Provider Delay | 日志 | 并发 |
|---|---:|---|---|
| 应用吞吐上限 | 0ms | INFO | 1/8/16/32/64 |
| 关闭高频日志对照 | 0ms | WARN | 1/8/16/32/64 |
| 快上游模拟 | 20ms | INFO | 1/8/16/32/64 |
| 慢上游模拟 | 100ms | INFO | 1/8/16/32/64 |
| 真实公网 | real | INFO | 1/2/5/10（谨慎） |

这样可以明确区分：

```text
OpenReach 自身容量
vs
日志开销
vs
上游等待造成的吞吐变化
vs
第三方 Provider 限流/反爬
```
