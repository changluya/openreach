# v0.1.3 三方渠道失败请求深度分析与兼容优化

> 分析对象：2026-08-17 导出的 23 条 OpenReach 失败请求详细日志。目标不是把所有上游错误“吞掉”，而是区分三方渠道真实限制与 OpenReach 自身兼容缺口，只修复我们能够安全负责的部分。

## 一、结论

23 条失败可归为三类：

| 类型 | 数量 | 结论 | 本次处理 |
|---|---:|---|---|
| Sogou HTTP 302 | 7 | **存在 OpenReach 兼容缺口**：搜索 HTTP 层没有把 Provider 的重定向作为受控协议处理 | 修复 |
| 360 Search HTTP 302 | 1 | **存在 OpenReach 兼容缺口**：同上，且旧入口 `/s` 稳定性较差 | 修复 |
| 百度 `http://www.baidu.com/link?...` Read 521 | 2 | **存在 OpenReach 结果 URL / Read 联动兼容缺口** | 修复 |
| Brave HTTP 429 | 3 | 三方限流 / 风控 | 保留真实失败；复用已有 cooldown / auto fallback |
| DuckDuckGo bot challenge | 2 | 三方反自动化挑战 | 保留真实失败；复用已有 cooldown / auto fallback |
| Baidu bot challenge | 2 | 三方反自动化挑战 | 保留真实失败；复用已有 cooldown / auto fallback |
| Read HTTP 403 | 4 | 目标站访问策略 / WAF / 反爬限制 | 不绕过；保留真实失败 |
| TLS SAN / certificate mismatch | 1 | 目标站证书配置异常 | 不关闭 TLS 校验 |
| 显式 `so360 + timeRange=week` 400 | 1 | OpenReach 主动 capability fail-fast，属于预期契约 | 不修改 |

因此，本次不是简单判断“都是三方问题”。**10 条失败存在我们可以安全修复的兼容路径，12 条属于真实上游限制，1 条属于正确的参数能力校验。**

## 二、问题 1：Sogou / 360 返回 302

### 现象

失败日志中 Sogou 连续返回 HTTP 302，360 也出现相同现象。旧 `SearchHttpClient` 依赖 JDK 自动重定向；对于免费 SERP 站点的入口迁移、绝对 Location、HTTPS/HTTP scheme 变化等情况，客户端无法获得足够明确且可控的兼容行为，最终直接把 302 暴露为 `UPSTREAM_ERROR`。

### 为什么属于我们的兼容缺口

HTTP 301/302/303/307/308 本身不是搜索失败，而是上游要求客户端切换请求目标。只要重定向仍处于对应 Provider 的可信域名族，并且次数受限，就应该由 HTTP 适配层处理，而不是让每个 Provider 重复实现。

### 本次优化

1. `SearchHttpClient` 改为 `Redirect.NEVER`，统一手工处理 301/302/303/307/308；
2. 新增 `openreach.web.search.max-redirects`，默认最多 5 次，防止重定向循环；
3. 只允许跳转到对应 Provider 的可信域名族，拒绝跨到未知 Host，避免新增 SSRF / Open Redirect 风险；
4. 如果 HTTPS 请求拿到 HTTP Location，不直接降级明文传输，而是在可信 Provider 域名内提升回 HTTPS；
5. 正确实现 301/302/303 与 307/308 的 Method 语义；
6. Sogou 增加 UTF-8 参数和首页 Referer；
7. 360 默认入口调整为 `https://www.so.com/index.php`，同时增加 UTF-8 参数和 Referer。

### 非目标

本次不会伪造 Cookie、绕 CAPTCHA、破解 WAF，也不会无限重试 302。若完成受控重定向后仍返回 403/429/挑战页，继续作为真实 Provider 失败进入 auto chain 降级。

## 三、问题 2：百度搜索结果 URL 与 Read 521

### 现象

日志中两条 Read 请求输入直接是：

```text
http://www.baidu.com/link?url=...
```

随后上游返回 521。这说明 Search 输出的仍是百度中转链接，Read 又把这个 legacy HTTP wrapper 当成最终内容页读取。

### 为什么属于我们的兼容缺口

搜索结果如果 HTML 中已经提供 `mu`、`data-landurl`、`data-url` 等落地地址，应优先输出真实 URL；即使只能得到百度 `/link` wrapper，也不应继续使用明文 HTTP 版本。

### 本次优化

1. `BaiduSearchProvider` 优先按 `data-landurl -> data-url -> block.mu -> block.data-url -> href` 提取落地地址；
2. 对无法解出落地页的百度 `/link` wrapper，统一把 legacy HTTP URL 升级为 HTTPS；
3. `SafeHttpFetcher` 再增加一层防御性规范化：调用方传入 `http://*.baidu.com/link?...` 时，先升级 HTTPS，再经过 `UrlSafetyGuard` 二次校验后访问；
4. 不对任意第三方 HTTP URL做强制升级，避免改变普通 Read 的协议语义。

这属于 Search 与 Read 边界上的“双保险”：优先从源头返回真实落地页，同时兼容历史数据或外部调用方传入的旧百度中转 URL。

## 四、哪些异常不能在代码里“修成成功”

### 1. Brave 429

这是上游明确限流。正确策略是 cooldown、auto provider fallback、降低请求频率，而不是立即对同一免费 SERP 重试形成更严重的限流。

### 2. Baidu / DuckDuckGo bot challenge

这是上游反自动化页面。OpenReach 应识别并快速失败，让 auto chain 尝试下一个 Provider；不应把挑战页 HTML 当成搜索结果。

### 3. Read 403

知乎及部分内容站点明确拒绝当前服务器访问方式。Blind retry 不会改变权限，伪造成功反而会污染 Agent 的事实来源。本版本继续返回真实 502/UPSTREAM_ERROR，由后续 Browser Reader / 合规代理能力单独演进。

### 4. TLS 证书 SAN 不匹配

`No subject alternative DNS name matching ...` 是目标站证书与 Host 不匹配。**禁止通过关闭 hostname verification / trust-all SSL 解决**，否则会引入中间人攻击风险。

### 5. `so360 + timeRange=week` 的 400

这是调用方显式指定一个不支持 week 的 Provider。当前接口已经明确返回 `BAD_REQUEST` 并建议 `provider=auto`，属于正确 fail-fast，不应该自动偷偷改写用户指定 Provider。

## 五、可观测性优化

`UpstreamFailureClassifier` 本次新增 / 细化：

- `TLS_CERTIFICATE`：证书链、SAN、SSL handshake；
- `HTTP_REDIRECT`：重定向缺 Location、超过限制或异常 3xx；
- `HTTP_5XX`：包含 521 等非标准但属于 5xx 范围的上游错误；
- 保留 `HTTP_403`、`HTTP_429`、`BOT_CHALLENGE`、`TIMEOUT`、`IO_ERROR` 等已有分类。

这样监控页面后续可以更准确地区分“上游风控”“站点证书”“Provider 重定向协议”“真实 5xx”。
