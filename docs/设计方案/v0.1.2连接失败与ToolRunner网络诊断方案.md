# v0.1.2 连接失败与 Tool Runner 网络诊断方案

## 1. 问题特征

当 Search / Read / Image Search 对完全不同的目标统一出现：

```text
All connection attempts failed
```

并且错误中**没有** OpenReach 标准字段：

```text
timestamp / status / code / traceId / message
```

优先判断为：**调用方（AgentHub / Tool Runner / Sandbox / Skill）没有连接到 OpenReach 服务本身**，而不是 Bing、百度、DuckDuckGo、Reuters、Techmeme 等所有上游同时失败。

OpenReach 后端已收到请求后的业务错误应由 `GlobalExceptionHandler` 返回结构化 JSON，并带 `traceId`。调用方 TCP/DNS/端口连接失败发生在 OpenReach 之前，因此后端无法生成 traceId。

## 2. 最常见根因：容器里的 localhost

如果：

```text
AgentHub / Tool Runner = Container A
OpenReach               = Container B
```

那么 Container A 中：

```text
http://localhost:8080
```

表示 **Container A 自己的 8080**，不是 Container B。

### 同一 Docker Network

使用 OpenReach 容器 / Compose Service DNS：

```text
http://openreach:8080
```

前提是两个容器确实加入同一个 Docker Network。

### Tool Runner 不在同一 Network

使用 Tool Runner 能访问到的宿主机 IP、内网域名、反向代理域名或公网域名：

```text
http://<reachable-host>:8080
https://<openreach-domain>
```

`BASE_URL` 的正确性必须从**Tool Runner 所在环境**验证，而不是只在 OpenReach 宿主机执行 curl。

## 3. v0.1.2 修复

### 3.1 AgentHub HTTP Plugin 不再默认 localhost

`docs/agenthub/skills/openreach-http-plugin.json`：

```json
{
  "baseUrl": "{{BASE_URL}}"
}
```

导入时必须显式配置 Tool Runner 可访问的 `BASE_URL`，避免容器环境把 `localhost` 误认为 OpenReach。

### 3.2 HTTP JSON 同时兼容 snake_case / camelCase

Tool Adapter 常把参数暴露为：

```json
{
  "time_range": "day",
  "max_chars": 50000
}
```

OpenReach canonical JSON 仍是：

```json
{
  "timeRange": "day",
  "maxChars": 50000
}
```

后端现在同时接受：

```text
timeRange / time_range
maxChars  / max_chars
```

这不是 `All connection attempts failed` 的根因，但可避免 Tool Adapter 参数命名转换后被静默忽略。

### 3.3 新增 caller-side 连接诊断脚本

```bash
BASE_URL=http://openreach:8080 \
./bin/quick/connectivity-test.sh
```

检查顺序：

```text
URL 合法性
  -> DNS
  -> TCP
  -> GET /
  -> POST /api/web/search {} = 400 VALIDATION_ERROR
```

最后一步只验证 API 可达性，不触发真实搜索 Provider。

如果脚本运行在容器里且 BASE_URL 使用 `localhost/127.0.0.1`，会主动给出警告。

## 4. 错误分类

| 表现 | 请求是否到 OpenReach | 优先排查 |
|---|---:|---|
| `All connection attempts failed`，无 traceId | 否 | BASE_URL、DNS、端口、容器网络、服务进程 |
| `HTTP connect timed out` + OpenReach traceId | 是 | OpenReach -> 目标网站网络出口 |
| `BOT_CHALLENGE` + traceId | 是 | Provider 反爬 / IP 信誉 |
| `HTTP 429` + traceId | 是 | Provider 限流 / cooldown |
| `HTTP 403` + traceId | 是 | 目标站访问策略 / Reader |
| `VALIDATION_ERROR` + traceId | 是 | 请求参数 |

## 5. 推荐现场排查

### OpenReach 宿主机

```bash
docker ps --filter name=openreach
docker logs --tail 100 openreach
curl -I http://127.0.0.1:8080/
```

### AgentHub / Tool Runner 所在环境

这一步最重要：

```bash
BASE_URL='<实际插件 BASE_URL>' ./bin/quick/connectivity-test.sh
```

如果宿主机 curl 成功、Tool Runner 失败，问题就在两者之间的网络拓扑，不需要继续修改 Search Provider。

### 同 Docker Network 示例

```bash
docker network create agent-net 2>/dev/null || true

docker run -d \
  --name openreach \
  --network agent-net \
  -p 8080:8080 \
  codercl/openreach:v0.1.2
```

AgentHub / Tool Runner 也加入 `agent-net` 后，插件使用：

```text
http://openreach:8080
```

## 6. 结论

本次大量 Search / Read 同时出现裸 `All connection attempts failed` 时，应先视为 **Tool Runner -> OpenReach 服务连接故障**。只有确认 caller-side connectivity 通过后，再分析 Search Provider 的 429 / Challenge 或 Read 上游超时。
