# v1.0.2 请求异常诊断与日志可观测优化方案

> 更新日期：2026-08-16  
> 目标：解决 `read` 403、Search Provider 全链失败时“只有最终 502、缺少中间证据”的排障问题，并为后续限流、退避、代理出口与 Browser Reader 演进建立统一观测基线。

---

## 1. 本次问题结论

### 1.1 `POST /api/web/read` 读取知乎返回 502 / 上游 403

现象：

```text
UPSTREAM_ERROR (502)
Upstream returned HTTP 403
```

OpenReach 的 502 是网关语义：真正的失败发生在目标网页上游，当前静态 `SafeHttpFetcher` 收到目标站点 HTTP 403 后转换为 `UPSTREAM_ERROR`。

403 可能来自以下任一因素，不能仅凭单次状态码断言为“同一 IP 请求次数过多”：

1. 出口 IP / ASN / 数据中心 IP 信誉；
2. 单 IP 短时间请求频率过高；
3. HTTP 请求头与真实浏览器指纹差异；
4. 缺少 Cookie、会话或首屏挑战流程；
5. JavaScript / CAPTCHA / WAF Challenge；
6. 地区、网络运营商或站点临时策略；
7. URL 本身仅允许浏览器交互式访问。

本次外部复核中，同一知乎文章 URL 从独立公网抓取环境也返回 403，因此问题至少不是“只在当前 OpenReach 宿主机偶发”。但由于不同出口环境仍可能共享“自动化访问”特征，所以仍不能排除 IP 信誉和频率因素。

### 1.2 Search 报 `All free search providers failed`

原始信息：

```text
bing: skipped (timeRange unsupported)
baidu: skipped (timeRange unsupported)
sogou: skipped (timeRange unsupported)
s0360: skipped (timeRange unsupported)
duckduckgo: duckduckgo bot challenge detected
```

这里要区分两类情况：

- Bing / Baidu / Sogou / 360：**在当时版本里根本没有发起网络请求**，因为请求携带 `timeRange`，而当时这些 Provider 尚未声明真实时间过滤能力，所以被能力路由主动跳过；
- DuckDuckGo：是真正执行了请求，但返回页面命中了 bot challenge 检测。

因此原始错误并不是“5 个搜索引擎都被当前单 IP 封禁”，而是“4 个因 capability 不满足被跳过 + 1 个实际请求被挑战”。

本次同时修复了这条链路的可用性退化：`timeRange!=any` 时不再直接沿普通 CN/GLOBAL 链逐个跳过，而是优先进入独立时间过滤链：

```text
旧修复：CN duckduckgo -> brave；GLOBAL brave -> duckduckgo
当前：  CN baidu -> bing -> duckduckgo -> brave
        GLOBAL bing -> brave -> duckduckgo -> baidu
```

restricted `timeRange` 的配置为空时**不再回退普通 Route Chain**。本轮进一步扩展零 Key 时间过滤能力：CN 默认 `baidu → bing → duckduckgo → brave`，GLOBAL 默认 `bing → brave → duckduckgo → baidu`。百度免费 Web 支持 `day/week/month/year`；Bing 免费 Web 已验证 `day/week/month`，`year` 会被能力路由跳过；Brave / DuckDuckGo 支持完整范围。SearchService 会按具体 `SearchTimeRange` 在运行期补入真正支持该范围的 Provider，避免旧配置导致单点退化。

本次优化后最终异常还会附带：

```text
attempted=<实际尝试数>
skipped=<主动跳过数>
```

便于第一眼判断到底是网络失败还是能力路由问题。

## 2. 本次已落地的代码优化

### 2.1 全请求 Trace ID

新增：

```text
observability/RequestTraceFilter.java
observability/TraceContext.java
```

每个请求生成：

```text
req-20260815T180351289-8f31a4c2
```

组成：

```text
req- + UTC 毫秒时间戳 + 8 位随机后缀
```

时间戳便于肉眼定位时段，随机后缀避免同毫秒并发冲突。

Trace ID 同时写入：

- MDC：`traceId`；
- API 日志；
- Provider / Read 上游日志；
- HTTP 响应头：`X-OpenReach-Trace-Id`；
- Spring MVC 错误 JSON：`traceId`；
- AttackSurfaceFilter 提前拒绝的错误 JSON：`traceId`。

后续排障：

```bash
grep 'req-20260815T180351289-8f31a4c2' /data/openreach/logs/openreach*.log
```

即可串起整个接口生命周期。

### 2.2 日志分层

新增 `src/main/resources/logback-spring.xml`：

```text
openreach.log
  完整应用日志

openreach-api.log
  API request_start / request_end / request_failed

openreach-upstream.log
  Search/Image Provider + Read 上游 HTTP 请求全过程
```

所有日志都包含：

```text
time
level
application
traceId
api
thread
logger
message
```

核心前缀：

```text
[OPENREACH-API]
[OPENREACH-SEARCH]
[OPENREACH-IMAGE]
[OPENREACH-READ]
[OPENREACH-UPSTREAM]
```

### 2.3 Provider 中间过程日志

Search 现在会记录：

```text
search_start
provider_skip
provider_start
http_start
http_response
provider_success
provider_fail
search_success / search_fail
```

典型日志：

```text
[OPENREACH-SEARCH] provider_skip provider=bing reason=UNSUPPORTED_CAPABILITY capability=timeRange value=week
[OPENREACH-SEARCH] provider_start provider=duckduckgo region=CN timeRange=week limit=5
[OPENREACH-UPSTREAM] http_response provider=duckduckgo status=403 host=html.duckduckgo.com latencyMs=412 contentType=text/html
[OPENREACH-SEARCH] provider_fail provider=duckduckgo type=HTTP_403 latencyMs=414 message=duckduckgo returned HTTP 403
```

### 2.4 Read 中间过程日志

Read 现在记录：

```text
read_start
http_start
http_response
redirect
http_io_fail
read_success / read_fail
```

日志只保留 Host / Path 等诊断字段，不默认把完整 query、Cookie、授权 Header 写日志。

### 2.5 失败分类

新增 `UpstreamFailureClassifier`，目前可识别：

```text
HTTP_403
HTTP_429
BOT_CHALLENGE
TIMEOUT
INTERRUPTED
RESPONSE_TOO_LARGE
PARSE_EMPTY
UNSUPPORTED_CAPABILITY
IO_ERROR
UPSTREAM_ERROR
```

后续可直接按分类统计 Provider 健康度，而不是解析自由文本。

### 2.6 Read 请求头基础补齐

Read 除现有 User-Agent / Accept 外，新增可配置：

```yaml
openreach.web.read.accept-language: zh-CN,zh;q=0.9,en;q=0.6
```

注意：这只是提升普通站点兼容性，不承诺绕过 WAF / CAPTCHA，也不建议每次请求随机拼装互相矛盾的浏览器 Header。

## 3. Logback 归档策略

默认日志目录：

```text
本地运行：./logs
Docker：/app/logs
```

可通过环境变量覆盖：

```bash
OPENREACH_LOG_PATH=/app/logs
```

当前归档策略：

| 日志 | 单文件上限 | 保留天数 | 总容量上限 |
|---|---:|---:|---:|
| `openreach.log` | 50 MB | 14 天 | 2 GB |
| `openreach-api.log` | 30 MB | 14 天 | 1 GB |
| `openreach-upstream.log` | 50 MB | 14 天 | 2 GB |

归档目录：

```text
/app/logs/archive/*.gz
```

同时保留 console 输出，继续支持：

```bash
docker logs -f openreach
```

Docker 自身 json-file 额外限制为：

```text
20 MB × 3 files
```

避免应用文件日志已归档但 Docker stdout 仍无限增长。

## 4. Docker 日志持久化

推荐宿主机固定目录：

```bash
sudo mkdir -p /data/openreach/logs
sudo chown -R 10001:10001 /data/openreach/logs
```

启动：

```bash
docker run -d \
  --name openreach \
  --restart unless-stopped \
  -p 8080:8080 \
  -e OPENREACH_LOG_PATH=/app/logs \
  -v /data/openreach/logs:/app/logs \
  codercl/openreach:1.0.2
```

容器删除 / 重建后：

```text
/data/openreach/logs
```

仍然保留历史日志。

Compose：

```bash
OPENREACH_LOG_DIR=/data/openreach/logs docker compose up -d
```

## 5. 推荐排障方式

### 5.1 根据接口返回 Trace ID 定位

错误响应示例：

```json
{
  "timestamp": "2026-08-15T17:53:51.289Z",
  "status": 502,
  "code": "UPSTREAM_ERROR",
  "traceId": "req-20260815T175351289-8f31a4c2",
  "message": "Upstream returned HTTP 403"
}
```

执行：

```bash
TRACE_ID=req-20260815T175351289-8f31a4c2
grep "$TRACE_ID" /data/openreach/logs/openreach-api.log
grep "$TRACE_ID" /data/openreach/logs/openreach-upstream.log

# 也可直接使用项目内置助手
OPENREACH_LOG_DIR=/data/openreach/logs ./bin/quick/logs.sh trace "$TRACE_ID"
```

### 5.2 快速看 403 / 429 / Bot Challenge

```bash
grep -E 'HTTP_403|HTTP_429|BOT_CHALLENGE|status=403|status=429' \
  /data/openreach/logs/openreach-upstream.log
```

### 5.3 看某个 Provider

```bash
grep 'provider=duckduckgo' /data/openreach/logs/openreach-upstream.log
```

### 5.4 判断是不是 `timeRange` 导致大量 Provider 未执行

```bash
grep 'reason=UNSUPPORTED_CAPABILITY' /data/openreach/logs/openreach-upstream.log
```

## 6. 单 IP / 代理池 / 请求头方案判断

### 6.1 单 IP 是否可能是原因？

**可能，但当前证据不足以单独归因。**

应至少通过一段时间日志统计以下矩阵：

```text
Provider × status × failureType × 时间窗口 × 请求频率
```

如果出现：

```text
低频正常 -> 高频逐渐 403/429 -> 冷却后恢复
```

才更支持“速率/IP 信誉”判断。

如果第一条请求就稳定 403，而浏览器正常，则更像：

```text
HTTP/TLS 指纹
Cookie / JS challenge
数据中心 ASN
站点明确拒绝自动化客户端
```

### 6.2 不建议直接做“随机请求头池”

把 UA、Sec-CH-UA、Accept-Language 等完全随机组合，容易形成不存在的浏览器指纹，反而提高异常率。

后续推荐做 **Header Profile**：

```text
chrome-mac-zh-cn
chrome-linux-en-us
openreach-explicit-bot
```

每个 Profile 内 Header 保持一致，并按 Provider 固定或低频切换，而不是每个请求随机生成。

### 6.3 代理能力建议定位为“出口路由池”，而不是 CAPTCHA 绕过器

Java `HttpClient.Builder.proxy(ProxySelector)` 原生支持代理选择，因此后续可以抽象：

```text
OutboundRouteProvider
  ├── DirectRoute
  ├── StaticProxyRoute
  ├── ProxyPoolRoute
  └── RegionRoute
```

代理池记录：

```text
proxyId
region
provider
successRate
403Rate
429Rate
latencyP95
cooldownUntil
lastFailureType
```

调度策略：

```text
1. 默认 Direct
2. Provider 明确允许代理且 Direct 连续出现可恢复网络失败 -> 切备用出口
3. 403 / 429 -> 进入 Provider + Route cooldown
4. 优先退避而不是立即换 IP 高频重试
5. CAPTCHA / JS challenge -> 不无限轮换代理，转 Browser/API Provider 或直接失败
```

## 7. 后续演进优先级

### P0：本次已完成

- Trace ID；
- API / Upstream 分文件日志；
- Logback 滚动归档；
- Docker Host 目录映射；
- HTTP status / latency / host / provider 日志；
- Provider skip / success / failure 分类；
- Search attempted / skipped 统计；
- `timeRange` 独立 Provider Chain，避免 CN 时间过滤请求退化为 DuckDuckGo 单路；
- Read `Accept-Language`；
- 错误响应携带 traceId。

### P1：推荐下一版

#### 1. Provider Rate Limiter + Cooldown

按 Provider 独立：

```text
maxConcurrency
minInterval
403Cooldown
429 Retry-After
failureWindow
```

避免多个 Agent 并发把同一免费 Provider 快速打进封禁窗口。

#### 2. Provider Circuit Breaker

例如 1 分钟内：

```text
连续 5 次 403 / BOT_CHALLENGE
-> OPEN 60s
-> 不继续无意义请求
-> HALF_OPEN 探测 1 次
```

#### 3. Header Profile

用一致的浏览器 Header 组替代“随机 Header”。

#### 4. 静态代理 / ProxySelector 抽象

先支持单代理配置与健康检查，再决定是否需要多出口池。

### P2：强反爬网页读取

静态 HTTP Reader 与 Browser Reader 分层：

```text
SafeHttpFetcher + Jsoup
    ↓ 403 / JS required / empty shell
BrowserReader (Playwright，可选组件)
```

Browser Reader 必须：

- 继续复用 SSRF Guard；
- 禁止任意文件下载/上传；
- 有并发上限和超时；
- 独立容器更安全；
- 尊重目标站点访问策略与服务条款。

### P3：商业/官方 API Provider

对于 Search 稳定性要求高的部署，免费 HTML SERP 永远只能 best-effort。建议保留：

```text
free provider chain
+ optional official/commercial API provider
```

由用户自行配置 Key，作为强 SLA fallback。

## 8. 为什么本次不直接上“无限代理池 + 随机 UA”

这类方案短期可能改变某些 403 表象，但会引入：

- 出口质量不可控；
- 数据泄露风险；
- Proxy 本身的 TLS / DNS / 地域问题；
- 重试风暴；
- 站点策略与合规风险；
- 更难复现问题。

因此当前优先顺序为：

```text
先可观测
-> 再限流/退避
-> 再 Provider 熔断
-> 再一致 Header Profile
-> 再可控代理出口
-> 强反爬页面走 Browser/API Adapter
```

这比直接用代理轮换“碰运气”更适合作为 OpenReach 的长期基础设施设计。
