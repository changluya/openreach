# OpenReach v0.1.2 优化（安全 + 海外）文档

> 基线版本：**v1.0.1**  
> 当前版本：**v0.1.2**  
> 状态：**已落地实现**  
> 文档职责：合并原《v0.1.2 设计落地方案》与《v0.1.2 安全加固设计》。  
> 核心目标：在不破坏 v1.0.1 国内免费渠道能力的前提下，完成 **CN / GLOBAL 双路由 + 海外零 Key 渠道 + Search 时间范围 + Image 可下载质量门禁 + 公网攻击面安全收敛**。

---

## 1. v0.1.2 解决什么问题

v1.0.1 已经具备：

```text
search(query)
image-search(query)
read(url)
```

并完成国内优先的多 Provider fallback。但 v1.0.1 的自动搜索只有一条全局 `provider-order`：

```text
bing -> baidu -> sogou -> so360 -> duckduckgo
```

即使请求明确传：

```json
{"query":"latest Java Agent frameworks","region":"US","provider":"auto"}
```

Service 仍然先走国内链，`region` 只是透传给 Provider，没有真正参与核心路由。

v0.1.2 将它改造为：

```text
region
  ↓
SearchRouteResolver
  ↓
ProviderChainResolver
  ├─ CN      -> 国内免费 Provider Chain
  └─ GLOBAL  -> 海外免费 Provider Chain
```

接口 DTO 不增加新字段，继续复用已有 `region`，因此对 AgentHub Plugin、Skill、已有调用方保持兼容。

## 2. v1.0.1 → v0.1.2 能力差异

| 能力 | v1.0.1 | v0.1.2 |
|---|---|---|
| Search 自动路由 | 单一 Provider Chain | **CN / GLOBAL 双链** |
| `region` | Provider best-effort Hint | **先决定核心 Route，再作为 Locale Hint 透传** |
| 默认 `region=auto` | 国内优先 | **仍为国内优先，兼容旧行为** |
| 海外 Web Search | DDG 兜底 | **Brave → DuckDuckGo → Bing Global** |
| Bing | 固定 `cn.bing.com` | **CN / Global Host 自动选择** |
| DuckDuckGo | GET 拼参数 | **HTML no-JS POST Form + Region/Cookie/Header + Challenge 识别** |
| Brave Web | 不支持 | **新增零 Key Provider** |
| 海外 Image Search | 无独立路由 | **Bing Global → Openverse → Wikimedia** |
| Wikimedia Commons | 不支持 | **新增公开读 API Provider** |
| Provider 配置 | `provider-order` | **新增 `cn-provider-order` / `global-provider-order`，旧字段继续兼容** |
| 路由扩展 | Service 内逻辑 | **`SearchRouteResolver + ProviderChainResolver` 集中路由与链配置，为 JP/EU/自定义 Route 留扩展点** |

## 3. 核心设计原则

### 3.1 Route 与 Locale 分离

`region` 同时携带两种信息，但代码不能把两种职责混为一层：

```text
region = US
│
├─ 路由语义：GLOBAL
│
└─ Provider Locale：US / en-US
```

因此新增：

```text
io.github.changlu.openreach.routing.SearchRoute
io.github.changlu.openreach.routing.SearchRouteResolver
io.github.changlu.openreach.routing.ProviderChainResolver
io.github.changlu.openreach.routing.RegionLocaleSupport
```

职责分别是：

```text
SearchRoute             -> 当前只定义 CN / GLOBAL
SearchRouteResolver     -> region -> Route
ProviderChainResolver   -> Route -> Web/Image Provider Chain
RegionLocaleSupport     -> Route + region -> country / locale / Accept-Language / DDG region
```

Provider 不再自己发明“什么叫海外”。需要 Route/Locale 感知时统一复用 routing 层；Service 也不直接判断 CN/GLOBAL 配置字段，而是消费 `ProviderChainResolver` 返回的链。

### 3.2 不根据 Query 语言判断 Route

以下请求仍走 GLOBAL：

```json
{"query":"OpenAI 最新进展","region":"US"}
```

以下请求仍走 CN：

```json
{"query":"Spring Boot AI Agent","region":"CN"}
```

**显式地域优先于 Query 文本语言。**

### 3.3 显式 Provider 优先级最高

```json
{"query":"OpenAI","region":"CN","provider":"brave"}
```

不会先进入 CN auto chain，而是直接调用 Brave。`region` 仍会作为 Brave 的 Locale Hint 使用。

## 4. Route 规则

当前 `SearchRouteResolver`：

```text
region = null / "" / auto
    -> openreach.web.routing.default-route
    -> 默认 CN

region = CN / zh-CN / zh_CN / cn-zh / zh-Hans-CN / china
    -> CN

其他显式 region
    -> GLOBAL
```

因此：

```text
US / en-US / GB / SG / JP / DE / GLOBAL / wt-wt
-> GLOBAL
```

当前只暴露两类内部 Route，是为了保持 v0.1.2 简洁；未来新增：

```text
JP
EU
CUSTOM
```

时无需改变 API DTO，只扩 Resolver 与 Route Policy。

## 5. v0.1.2 Web Search 路由

### 5.1 CN

```text
bing (cn.bing.com)
  ↓
baidu
  ↓
sogou
  ↓
so360
  ↓
duckduckgo
```

保持 v1.0.1 主路径，避免国内能力回归。

### 5.2 GLOBAL

```text
brave
  ↓
duckduckgo
  ↓
bing (www.bing.com)
```

选择原因：

- 全部默认无需 API Key；
- Brave Web 有持续维护的公开 Web Interface 适配参考；
- DDG 有 HTML/Lite no-JS 路径；
- Bing Global 复用现有成熟 Parser，只切 Host / Locale；
- 三路索引来源并不完全相同，可降低单渠道依赖。

### 5.3 Brave Search Provider

新增：

```text
BraveSearchProvider
```

请求：

```text
https://search.brave.com/search?q=...&source=web
```

并设置：

```text
Accept-Language
safesearch Cookie
useLocation=0
summarizer=0
country
ui_lang
```

Parser 只解析真实结果块，不处理广告或 Brave 内部相对链接。

### 5.4 DuckDuckGo 强化

v0.1.2 不再用简单 GET Query 模拟 DDG HTML，而改为更符合当前 no-JS 页面流程的：

```text
POST https://html.duckduckgo.com/html/
Content-Type: application/x-www-form-urlencoded

q=...
b=
kl=...
```

同时增加：

```text
Referer
Sec-Fetch-Mode
Accept-Language
kl Cookie
```

并显式识别 bot challenge；发现 challenge 后立即抛 Provider 失败，让 Auto Chain 进入下一路，不建设 CAPTCHA 绕过。

### 5.5 Bing 全球化

同一个 `BingSearchProvider` 根据 Route 选择：

```text
CN     -> https://cn.bing.com/search
GLOBAL -> https://www.bing.com/search
```

不复制 `BingGlobalSearchProvider`，减少 Parser 重复维护。

## 6. v0.1.2 Image Search 路由

### 6.1 CN

```text
bing-cn -> baidu -> sogou -> openverse
```

保持原能力。

### 6.2 GLOBAL

正式落地：

```text
bing-global -> openverse -> wikimedia
```

### 6.3 为什么没有把 Brave Images 放 P0

前期调研确认 Brave Standard Web Interface 能覆盖 Images，但当前图片结果主要藏在页面内嵌 Svelte/JS 状态中，结构比 Brave Web DOM 更脆弱。

v0.1.2 的工程目标是：

> **少而稳，不为了 Provider 数量把高维护成本 Parser 放进默认链。**

因此 Brave Images 从原设计 P0 调整为观察项；等形成稳定 Fixture 与长期 Smoke 数据后再决定是否接入。

### 6.4 Wikimedia Commons

新增：

```text
WikimediaImageSearchProvider
```

使用公开 MediaWiki Action API：

```text
generator=search
gsrnamespace=6
prop=imageinfo
iiprop=url|size|mime|extmetadata
```

统一映射：

```text
imageinfo.url             -> imageUrl
imageinfo.thumburl        -> thumbnailUrl
imageinfo.descriptionurl  -> sourcePageUrl
width / height / mime     -> 图片信息
LicenseShortName          -> license
LicenseUrl                -> licenseUrl
```

并使用单独的可识别 User-Agent：

```yaml
wikimedia-user-agent: OpenReach/0.1.2 (+https://github.com/changluya/openreach)
```

## 7. 配置模型

```yaml
openreach:
  web:
    routing:
      default-route: cn

    search:
      provider: auto

      # v1.0.1 兼容字段
      provider-order:
        - bing
        - baidu
        - sogou
        - so360
        - duckduckgo

      # 默认留空并继承 provider-order，保证 v1.0.1 外部配置兼容。
      cn-provider-order: []

      global-provider-order:
        - brave
        - duckduckgo
        - bing

      bing-url: https://cn.bing.com/search
      bing-global-url: https://www.bing.com/search
      brave-url: https://search.brave.com/search
      duckduckgo-url: https://html.duckduckgo.com/html/

    image-search:
      provider: auto

      provider-order:
        - bing
        - baidu
        - sogou
        - openverse

      # 默认留空并继承 provider-order。
      cn-provider-order: []

      global-provider-order:
        - bing
        - openverse
        - wikimedia

      bing-url: https://cn.bing.com/images/async
      bing-global-url: https://www.bing.com/images/async
      openverse-url: https://api.openverse.org/v1/images/
      wikimedia-url: https://commons.wikimedia.org/w/api.php
```

### 7.1 兼容策略

如果旧部署只有：

```yaml
provider-order:
  - ...
```

且 `cn-provider-order` 未配置或为空，CN Route 自动继续使用旧 `provider-order`。项目内置 `application.yml` 也刻意把 `cn-provider-order` 保持为空，避免外部 v1.0.1 配置被新默认值遮蔽。

因此旧的国内部署配置不会因为升级 v0.1.2 立即失效。

## 14. v0.1.2 持续优化：Search 时间范围

本轮继续保持版本号 **v0.1.2**，在既有 CN / GLOBAL Route 上补充统一 `timeRange`：

```json
{
  "query": "latest Java AI Agent frameworks",
  "region": "US",
  "provider": "auto",
  "timeRange": "month"
}
```

标准值：`any / day / week / month / year`。兼容常见 `d/w/m/y`、`pd/pw/pm/py`、`qdr:*` 写法，但 Service 内部统一转换为 `SearchTimeRange` 枚举。

扩展设计：

```text
SearchRequest
  -> SearchTimeRange.parse
  -> SearchService
  -> SearchProvider.supportsTimeRange(timeRange)
     ├─ false + auto      -> skip
     ├─ false + explicit  -> BAD_REQUEST
     └─ true              -> provider-specific mapping
```

`SearchProvider` 原三参数方法继续作为抽象方法保留，因此 v1.0.1 第三方 Provider 仍可直接加载；时间范围通过 default capability 方法增量扩展，不破坏旧 SPI。

当前实现：百度免费 Web 已按真实结果页 `gpc/stf + timefactor` 参数实现 `day/week/month/year`；Bing 免费 Web 已按 `filters=ex1:"ez1/ez2/ez3"` 实现 `day/week/month`，其 `year` 免费网页参数未得到稳定验证，因此不伪造支持；Brave、DuckDuckGo 继续支持真实上游时间过滤。

## 15. v0.1.2 持续优化：Image 可下载质量门禁

Image Search 从“发现 URL”升级为“返回当前真正可取得的图片 URL”。

```text
Image Provider
  -> 候选 over-fetch
  -> SecureImageDownloadVerifier
     -> UrlSafetyGuard
     -> Redirect re-check
     -> GET/Range prefix
     -> HTTP 2xx
     -> Content-Type reject HTML/XML/SVG
     -> Passive image magic bytes
  -> Downloadable Result
  -> dedupe / rank / limit
```

设计上把验证器抽为 `ImageDownloadVerifier` SPI，Service 不绑定具体网络探测实现；后续可扩缓存、CDN Probe、质量评分或异步健康状态，而不改变 Image Provider SPI。

`provider=auto` 时，如果某一路“搜得到但下载不了”，将继续下一 Provider；显式 Provider 则 fail-fast，避免给 Agent 返回无用 URL。

## 16. v0.1.2 持续优化：安全攻击面收敛

v0.1.2 将 OpenReach 明确收敛为“三个 JSON API + 只读官网静态资源”的最小公网攻击面，禁止上传/写文件，并强化所有用户可控远程 URL 的 SSRF 防护。

### 16.1 公网 Allowlist

业务 API 只有：

```text
POST /api/web/search
POST /api/web/image-search
POST /api/web/read
```

只读网站资源：

```text
/
/index.html
/docs[/]
/docs/index.html
/docs/api.html
/community[/]
/changelog[/]
/assets/**
/downloads/openreach-skill.zip
```

其他路径默认 `404`，避免未来误加 Controller、Actuator 或调试端点后自动暴露。

### 16.2 上传与文件植入防护

应用不提供任何上传/保存文件业务，采用双层关闭：

1. `AttackSurfaceFilter` 拒绝所有 `multipart/*`；
2. `spring.servlet.multipart.enabled=false`；
3. API 只接受 `application/json`；
4. 静态资源只来自 `classpath:/static/`，不映射宿主文件目录；
5. Docker 部署采用非 root、只读根文件系统、`no-new-privileges`、`cap_drop: ALL`。

因此 HTTP 请求不能把任意文件写入官网目录或应用工作目录。

### 16.3 HTTP 方法与请求体

- API：仅 POST；
- 静态资源：仅 GET/HEAD；
- PUT/PATCH/DELETE/TRACE 等拒绝；
- API Body 默认最大 64 KiB；
- 同时检查 Content-Length 和真实流读取，避免 chunked 绕过；
- Query / URL / region / provider / timeRange 继续由 Bean Validation 与业务解析限制。

### 16.4 Path Traversal

Filter 在 Dispatcher 前拒绝：

```text
..
反斜线
分号 path parameter
任意 percent-encoded path
控制字符
```

静态资源又只允许固定路径和 `/assets/**`，形成 allowlist + classpath 双重边界。

### 16.5 Read / Image SSRF

`UrlSafetyGuard` 是用户 URL 和图片候选 URL 的统一安全边界：

- 只允许 HTTP/HTTPS；
- 只允许 80/443；
- 禁止 user-info；
- 禁止 localhost、`.local`、`.internal`、云元数据主机；
- DNS 解析结果禁止 loopback、RFC1918、link-local、CGNAT、benchmark、TEST-NET、multicast、IPv6 ULA/文档段等；
- 每次重定向重新校验目标；
- Read 限制 redirect/body；Image Probe 限制 redirect/timeout/read prefix。

> 应用层 DNS 校验无法替代网络层出口控制。生产环境仍建议用容器/防火墙 egress ACL 禁止访问 RFC1918、link-local 和云元数据网段，形成纵深防御。

### 16.6 图片内容安全

Image Search 返回前只读取小段原图字节用于验证：

- HTTP 2xx；
- 拒绝 text/html/xml；
- 明确拒绝 SVG 主动内容；
- 只接受 JPEG/PNG/GIF/WebP/BMP/TIFF/ICO/AVIF/HEIC 等已知被动图片签名；
- 不执行脚本、不解析图片元数据、不保存文件。

### 16.7 官网浏览器安全

统一响应头：

```text
Content-Security-Policy
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: no-referrer
Permissions-Policy
Cross-Origin-Opener-Policy
Cross-Origin-Resource-Policy
```

官网主题初始化脚本从 inline script 移为 `/assets/theme-init.js`，使 `script-src 'self'` 无需 `unsafe-inline`。

官网复制按钮统一采用：

```text
Clipboard API（安全上下文优先）
  -> 失败/不可用
selection + execCommand('copy') fallback
```

因此直接通过 `http://IP:8080` 访问时也能正常复制命令，并提供成功/失败状态反馈。

### 16.8 上游资源上限

搜索页和图片搜索 Provider 的 HTML / JSON 不再使用无界 `ofByteArray()`：

- Web Search 上游响应默认最大 2 MiB；
- Image Search Provider 上游响应默认最大 4 MiB；
- 同时检查 `Content-Length` 和流式真实读取大小；
- 超限立即关闭响应流并作为当前 Provider 失败处理；
- Read 原有 `max-bytes` 边界继续保留；
- Image Probe 只读取小段文件头，不下载完整图片到服务端；
- Probe Executor 使用固定并发 + 有界队列（默认 48）+ CallerRuns 背压，避免公网高并发把验证任务无界堆入内存。

### 16.9 依赖安全基线

当前 `pom.xml` 使用 Spring Boot `4.1.0`。工程同时采用 `classpath:/static/` + `AttackSurfaceFilter` 路径 allowlist，不依赖框架自身修复作为唯一安全边界。

正式发布仍建议执行：

```text
mvn dependency:tree
依赖漏洞扫描
镜像漏洞扫描
```

并确认实际解析依赖未被外部 BOM/父工程覆盖。

### 16.10 错误信息

- 参数错误返回可操作的客户端错误；
- 未知服务端异常只在服务端日志保留细节；
- 客户端统一收到泛化 `Internal server error`，避免堆栈/实现细节泄露。

### 16.11 必测安全 Case

```text
仅三个 API 能进入应用链
/api/web/health -> 404
/actuator/* -> 404
/upload / /api/upload -> 404
multipart -> 415 UPLOAD_DISABLED
非预期 Method -> 405
超大 Body -> 413
../ / encoded traversal -> 400
静态官网包含 CSP 等安全 Header
localhost / metadata / private / CGNAT / TEST-NET -> SSRF reject
图片 Probe 对 localhost -> false
HTML/SVG/随机字节 -> 非图片
Search/Image Provider 超大上游 Body -> 拒绝
所有官网 data-copy selector -> 必须存在目标节点
HTTP 与 HTTPS 两种复制路径 -> 均有回归覆盖
```

### 16.12 安全边界声明

OpenReach v0.1.2 不把“安全”描述为绝对无漏洞。应用层已把当前已知公网攻击面最小化，但生产环境仍应持续做依赖漏洞扫描、镜像升级、WAF/限流、出口 ACL、日志告警与版本升级。

## 17. 本轮兼容性结论

| 项目 | v1.0.1 / 既有 v0.1.2 调用 | 本轮行为 |
|---|---|---|
| Search 不传 `timeRange` | 无需修改 | 等价 `any` |
| 第三方 SearchProvider | 原三参数 SPI | 无需修改，默认 `supportsTimeRange=false` |
| Image Search 请求协议 | 无新增必填字段 | 无需修改，但输出质量变强 |
| Skill / Plugin | 原能力继续可用 | 增加时间参数并声明图片下载保证 |
| Health API | 旧文档曾提供 | 为收敛公网攻击面已移除；Skill doctor 改为只读 `GET /` |
| 三个核心 API | 保持路径和方法 | 完全兼容 |

## 18. v0.1.2 最终结论

v0.1.2 的重点不是单纯增加 Provider 数量，而是完成两次结构升级：

```text
v1.0.1：国内优先单链 Provider Aggregator
   ↓
v0.1.2：Region-aware Web Access Router
          + 最小公网攻击面
          + 可下载图片质量门禁
```

在保持 Search / Image Search / Read 三大外部 API 主路径稳定的同时，路由、渠道、质量与安全能力都被下沉为可独立演进的基础层。
