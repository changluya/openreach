# OpenReach v0.1.3 设计方案文档

> 版本定位：v0.1.3 在现有 Search / Image Search / Read 能力基础上，新增一个**不在官网公开导航中展示的内部调用监控后台**，并完成真实请求采集、SQLite 单机持久化、日期统计、失败下钻、请求详情、容器持久化目录与 Schema Migration。存储访问统一收敛到 `MonitorRecordStore`，为后续迁移 MySQL / PostgreSQL 等服务型数据库保留稳定扩展边界。

---

## 1. v0.1.3 目标与边界

### 1.1 本版本已落地

- 独立内部访问地址：`/monitor`；
- 官网首页、Docs、更新日志页面不展示监控入口；
- 服务端 Session 登录保护；
- 默认账号密码：`openreach / openreach`；
- 支持 Docker Run / Docker Compose 通过环境变量覆盖默认用户名密码，首次启动、销毁重建与版本升级均可重新指定；
- 数据总览支持“今日 / 近 7 日 / 自定义日期范围”；
- 展示调用次数、成功数量、失败数量、独立 IP 数、成功率、平均耗时、P95；
- 展示调用趋势与接口调用分布；
- 点击失败数量可自动下钻失败请求；
- 请求记录包含请求时间、IP、输入参数、请求接口、输出参数、请求状态、HTTP 状态、耗时、Trace ID；
- 请求详情通过抽屉查看真实输入 / 输出与错误信息；
- 失败请求筛选态支持一键导出，导出复用当前日期范围 / Endpoint / Keyword，并包含全部匹配记录的完整入参、返回值、错误信息与 Trace ID；
- 三个公开 API 的调用结果由 `RequestTraceFilter` 自动采集；
- 采集事件通过有界队列异步写入，不在 API 请求线程同步 INSERT；
- 默认启用 SQLite + WAL，数据库位于 `/app/data/monitor/openreach-monitor.db`；
- 元数据与 Payload 分表，默认元数据保留 30 天、Payload 保留 7 天；
- `/api/monitor/*` 已作为真实查询 API 接入监控页面；
- `monitor_schema_version` + 顺序 Migration 已落地，当前 Schema Version 为 V2；V2 在升级前一致性快照后修复历史可识别的 UTF-8/Latin-1 乱码 Payload；
- Docker Compose 增加一次性 `openreach-init`，自动处理宿主机 data/logs 目录权限。

### 1.2 本版本真实持久化边界

v0.1.3 已从前端 Mock 切换到真实数据链路：

```text
/api/web/*
   ↓
RequestTraceFilter
   ↓
MonitorEventPublisher
   ↓
Bounded Queue
   ↓
MonitorService / Single Writer
   ↓
MonitorRecordStore
   ↓
SqliteMonitorRecordStore
   ↓
/app/data/monitor/openreach-monitor.db
```

当前只内置 `sqlite` 存储实现，但 Controller、采集 Filter、异步 Writer 和 UI 均不依赖 SQLite 类。未来增加 MySQL / PostgreSQL 时，只新增对应 `MonitorRecordStore` 实现与该数据库的 migration，不修改上层调用协议。

## 2. 内部监控后台设计

### 2.1 访问模型

```text
用户知道内部 URL
      │
      ▼
GET /monitor
      │
      ├── 未登录 → /monitor-login
      │
      └── 已登录 → Monitor Dashboard
```

默认凭据：

```text
username: openreach
password: openreach
```

生产环境建议覆盖：

```bash
OPENREACH_MONITOR_USERNAME=admin
OPENREACH_MONITOR_PASSWORD='change-me'
```

Docker Run：

```bash
docker run -d \
  --name openreach \
  --restart unless-stopped \
  -p 8080:8080 \
  -e OPENREACH_MONITOR_USERNAME=admin \
  -e OPENREACH_MONITOR_PASSWORD='change-me' \
  -v /data/openreach/data:/app/data \
  -v /data/openreach/logs:/app/logs \
  codercl/openreach:0.1.3
```

Docker Compose：

```bash
OPENREACH_MONITOR_USERNAME=admin \
OPENREACH_MONITOR_PASSWORD='change-me' \
OPENREACH_IMAGE=codercl/openreach:0.1.3 \
  docker compose up -d --force-recreate
```

账号密码**不属于监控业务数据，也不会写入 `/app/data/monitor/openreach-monitor.db`**。它们只由当前容器环境变量注入，因此升级时可以自由修改；若希望升级后继续使用同一凭据，则在新容器启动时继续传入相同环境变量。数据目录与凭据生命周期相互独立：销毁容器不会丢监控数据，修改登录凭据也不需要迁移数据库。

### 2.2 为什么不在官网暴露入口

监控后台属于部署实例的运维能力，不属于 OpenReach 对外能力展示，因此：

- 不加入官网导航；
- 不加入 Docs 公开菜单；
- 不通过首页按钮引导进入；
- 只给实际部署 / 运维人员约定 URL；
- 即使知道 URL，也必须先通过服务端登录校验。

“隐藏 URL”只降低暴露度，真正的安全边界仍然是服务端鉴权。

## 4. 失败请求下钻设计

失败数量不是只展示一个数字，而是一个可操作入口：

```text
失败数量卡片
    │ click
    ▼
自动设置 status=failure
    │
    ▼
定位到请求记录表
    │
    ▼
点击某条“详情”
    │
    ▼
请求详情抽屉
```

请求记录区在 `status=failure` 时额外显示“导出失败请求”按钮。导出接口复用同一组筛选条件，但忽略 `page/pageSize`，因此导出的是**全部匹配失败记录**而不是当前页。

详情至少展示：

- 请求时间；
- Trace ID；
- Client IP；
- HTTP Method；
- 请求接口；
- 输入参数；
- 输出参数；
- HTTP Status；
- Success / Failed；
- Provider；
- Error Code；
- Error Message；
- 耗时。

## 5. 真实数据 API（v0.1.3 已实现）

监控前端当前直接调用以下服务端接口；所有接口都受 Monitor Session 鉴权保护：

```http
GET /api/monitor/status
GET /api/monitor/overview?startTimeMs=...&endTimeMs=...
GET /api/monitor/trend?startTimeMs=...&endTimeMs=...&bucket=day&timezoneOffsetMinutes=-480
GET /api/monitor/distribution?startTimeMs=...&endTimeMs=...
GET /api/monitor/records?startTimeMs=...&endTimeMs=...&page=1&pageSize=20&status=failure&endpoint=...
GET /api/monitor/records/export?startTimeMs=...&endTimeMs=...&status=failure&endpoint=...&keyword=...
GET /api/monitor/records/{traceId}
```

### 5.1 Overview

返回：

```json
{
  "total": 1240,
  "success": 1188,
  "failure": 52,
  "uniqueIpCount": 186,
  "successRate": 95.81,
  "avgLatencyMs": 632,
  "p95LatencyMs": 1680,
  "droppedEvents": 0
}
```

### 5.2 Records

请求记录列表只返回摘要字段，大字段 payload 不应在列表接口中批量返回；只有点详情时才读取完整 request / response payload。

这样可以避免 20 条记录每条携带几十 KB / 几百 KB JSON，导致页面和数据库都做无意义 IO。

### 5.3 Failure Export

`/api/monitor/records/export` 使用与记录列表相同的筛选语义：

```text
startTimeMs / endTimeMs
status
endpoint
keyword
```

前端在失败下钻态固定传 `status=failure`。点击“导出失败请求”后，浏览器通过 `fetch` 请求后端 `/api/monitor/records/export`，后端通过 `MonitorRecordStore.streamDetails(...)` 流式读取全部匹配详情并生成 UTF-8 `.log` 诊断日志，不将所有 Payload 一次性堆入 JVM 内存，也不受页面 `page/pageSize` 限制。

日志文件顶部包含导出时间、时间范围、Endpoint / Keyword 筛选条件和匹配失败总数；每条失败请求独立分段，包含请求时间、Client IP、Trace ID、HTTP Method / Endpoint、HTTP Status、耗时、Provider、Error Code / Message、Payload 大小/截断状态，以及完整 request / response payload。响应通过 `Content-Disposition: attachment` 触发下载，并携带 `X-OpenReach-Export-Count`。

该能力仍然只依赖 Store SPI；未来切换 MySQL / PostgreSQL，只需各 Store 提供等价的流式迭代实现。

# 第二部分：真实请求采集与单机持久化设计

## 6. 持久化结论

### 6.1 当前推荐

**单机默认：SQLite + WAL + JDBC + Schema Migration。**

**未来扩展：上层只依赖 `MonitorRecordStore`，可增加 `sqlite | mysql | postgresql` 实现。**

当前不建议为了一个内部调用监控后台强制额外部署 MySQL / PostgreSQL，也不建议把 H2、DuckDB、RocksDB 作为请求明细的长期默认主存储。

核心原因：

1. OpenReach 当前核心体验是一条 Docker 命令即可启动；
2. SQLite 不需要额外 DB Server、账号、端口和初始化流程；
3. 请求明细天然需要时间范围、状态、接口、IP、Trace ID、分页、COUNT / GROUP BY；
4. SQLite SQL 与索引模型和这类需求高度匹配；
5. WAL 模式适合“持续写日志 + 后台持续查询”的单机模型；
6. 单 writer 可以通过“有界队列 + 单写线程 + batch”主动规避；
7. 未来真正进入多实例或已有外部数据库基础设施时，再按部署需要切换 MySQL / PostgreSQL。

## 7. 存储引擎对比

| 方案 | 单机零依赖 | Java 接入 | 明细 SQL | 聚合统计 | 多写并发 | 升级体验 | 运维成本 | 当前结论 |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| **SQLite + WAL** | ★★★★★ | ★★★★☆ | ★★★★★ | ★★★★☆ | ★★★☆☆ | ★★★★★ | ★★★★★ | **首选** |
| H2 Embedded | ★★★★★ | ★★★★★ | ★★★★★ | ★★★★☆ | ★★★★☆ | ★★★☆☆ | ★★★★☆ | 不作为长期默认 |
| DuckDB | ★★★★★ | ★★★★☆ | ★★★★☆ | ★★★★★ | ★★★☆☆ | ★★★★☆ | ★★★★☆ | 更适合 OLAP |
| RocksDB | ★★★★★ | ★★★☆☆ | ★★☆☆☆ | ★★☆☆☆ | ★★★★★ | ★★★☆☆ | ★★★☆☆ | 查询模型不匹配 |
| MySQL 8.x | ★★☆☆☆ | ★★★★★ | ★★★★★ | ★★★★★ | ★★★★★ | ★★★★★ | ★★☆☆☆ | 可选服务型存储 |
| PostgreSQL | ★★☆☆☆ | ★★★★★ | ★★★★★ | ★★★★★ | ★★★★★ | ★★★★★ | ★★☆☆☆ | **未来多实例首选** |

### 7.1 SQLite

适合当前单 JVM / 单容器模式：单文件、SQL 查询能力完整、部署成本低、文件格式长期稳定。

主要限制：

- 一个 SQLite DB 同一时刻只有一个 writer；
- 不应把 WAL SQLite 文件当成跨主机共享数据库放到 NFS / SMB；
- 查询必须分页，避免后台长时间事务影响 checkpoint。

### 7.2 H2

H2 的 Java 集成非常自然，但历史上跨大版本文件兼容需要更加谨慎。OpenReach 希望用户“拉新镜像 + 重建容器”后尽量自动升级，因此长期持久化优先选择文件格式兼容性和独立性更强的 SQLite。

### 7.3 DuckDB

DuckDB 更适合进程内 OLAP、大扫描和复杂聚合。未来可以用于历史离线分析，但不作为持续写入的在线请求明细主库。

### 7.4 RocksDB

RocksDB 是 KV / LSM 模型。OpenReach Monitor 需要多条件 SQL、排序、分页与聚合，用 RocksDB 会迫使项目自己维护大量二级索引和查询逻辑，复杂度收益比不高。

### 7.5 MySQL / PostgreSQL

当 OpenReach 进入多实例、多主机并发写、集中化监控、HA / 托管数据库阶段，应切换客户端-服务器数据库。项目通过 `MonitorRecordStore` 隔离数据库差异：已有 MySQL 基础设施的用户可以选择 MySQL；需要更强 SQL/分析能力或默认新建服务型存储时优先 PostgreSQL。

## 8. 真实采集链路

```text
/api/web/search
/api/web/image-search
/api/web/read
       │
       ▼
RequestTrace / MonitorCapture Filter
       │
       │ 仅采集，不同步写 DB
       ▼
Bounded Monitor Queue
       │
       ▼
Single Monitor Writer
  ├─ batch insert
  ├─ short transaction
  └─ failure isolation
       │
       ▼
SQLite + WAL
/app/data/monitor/openreach-monitor.db
       │
       ├── overview query
       ├── trend query
       ├── records paging
       └── request detail
       │
       ▼
/api/monitor/*
       │
       ▼
/monitor
```

### 8.1 为什么不能在请求线程同步 INSERT

核心 Web API 请求完成后只负责把事件投递给队列：

```java
monitorQueue.offer(event);
```

由后台单 writer 批量落库，例如：

```text
每 100 条
或
每 200ms
```

满足任一条件就提交一次。

原则：

> Monitor 故障不能导致 Search / Image Search / Read 故障。

队列真的满时，优先：

1. 丢弃超大 payload；
2. 记录 dropped monitor events 指标；
3. 必要时丢弃本条监控事件；
4. 三个核心 Web API 继续正常返回。

## 9. SQLite Schema V2（已落地）

v0.1.3 不再使用一张超级宽表，而是把“高频统计元数据”和“大 Payload”拆开。

### 9.1 Schema Version

```sql
CREATE TABLE monitor_schema_version (
    version       INTEGER PRIMARY KEY,
    description   TEXT NOT NULL,
    applied_at_ms INTEGER NOT NULL
);
```

当前最新版本：`V2`。V1 负责建表与索引，V2 是程序化数据 migration，用于修复历史监控 Payload 中可明确识别的 UTF-8 被 Latin-1/ISO-8859-1 误解码问题。

```text
src/main/resources/db/monitor/sqlite/V001__init.sql
Schema V2: SqliteMonitorRecordStore.repairLegacyPayloadEncoding(...)
```

升级到 V2 前会先执行现有 `VACUUM INTO` 一致性快照，再在事务中完成修复；正常 UTF-8、ASCII 和不能安全判定的字符串不会被强制转换。

### 9.2 请求元数据表

```sql
CREATE TABLE monitor_request_record (
    id                  INTEGER PRIMARY KEY AUTOINCREMENT,
    trace_id            TEXT NOT NULL UNIQUE,
    request_time_ms     INTEGER NOT NULL,
    client_ip           TEXT,
    method              TEXT NOT NULL,
    endpoint            TEXT NOT NULL,
    http_status         INTEGER NOT NULL,
    success             INTEGER NOT NULL,
    latency_ms          INTEGER NOT NULL,
    provider            TEXT,
    error_code          TEXT,
    error_message       TEXT,
    payload_truncated   INTEGER NOT NULL DEFAULT 0,
    created_at_ms       INTEGER NOT NULL
);
```

### 9.3 Payload 表

```sql
CREATE TABLE monitor_request_payload (
    record_id        INTEGER PRIMARY KEY,
    request_payload  TEXT,
    response_payload TEXT,
    request_bytes    INTEGER NOT NULL DEFAULT 0,
    response_bytes   INTEGER NOT NULL DEFAULT 0,
    created_at_ms    INTEGER NOT NULL,
    FOREIGN KEY(record_id) REFERENCES monitor_request_record(id) ON DELETE CASCADE
);
```

### 9.4 索引

```sql
CREATE INDEX idx_monitor_request_time
    ON monitor_request_record(request_time_ms DESC);
CREATE INDEX idx_monitor_status_time
    ON monitor_request_record(success, request_time_ms DESC);
CREATE INDEX idx_monitor_endpoint_time
    ON monitor_request_record(endpoint, request_time_ms DESC);
CREATE INDEX idx_monitor_http_status_time
    ON monitor_request_record(http_status, request_time_ms DESC);
```

拆表后的直接收益：总览、趋势、成功失败和接口分布只扫描 `monitor_request_record`；7 天后可只删除 `monitor_request_payload`，不影响 30 天元数据统计。

时间统一使用 epoch millisecond，避免 DB 时区语义，并降低未来 SQLite → MySQL / PostgreSQL 的转换成本。

## 10. Payload 保存与磁盘控制

输入 / 输出需要支持详情查看，但不能无限保存。

建议默认：

```yaml
openreach:
  web:
    monitor:
      persistence-enabled: true
      storage: sqlite
      data-dir: ./data/monitor
      sqlite-file: openreach-monitor.db
      queue-capacity: 10000
      batch-size: 100
      flush-interval-ms: 200
      metadata-retention-days: 30
      payload-retention-days: 7
      max-payload-bytes: 65536
```

规则：

1. 元数据默认保留 30 天；
2. 完整 request / response payload 默认保留 7 天；
3. 8～30 天只保留时间、IP、接口、状态、耗时、Trace ID、错误摘要等元数据；
4. 超大 payload 截断并设置 `payload_truncated=1`；
5. JSON Payload 入库前对 `Authorization/Cookie/password/token/secret/apiKey/accessToken` 等高风险字段做脱敏；
6. Payload 搜索只作为后台辅助能力，不对其建立重型全文索引；
7. `trust-proxy-headers=true` 默认开启，但仅当 `remoteAddr` 命中 `trusted-proxy-cidrs`（默认 loopback + Docker `172.16.0.0/12`）时读取 `X-Forwarded-For/X-Real-IP`；代理链从右向左剥离可信节点，避免直接客户端伪造 Header 污染监控 IP。

### 10.1 Payload 字符集约束

监控采集保存的是 HTTP body 字节，因此字符集判断必须基于响应 `Content-Type`：

1. 明确包含 `charset=...` 时按声明字符集解码；
2. `application/json` / `+json` 未声明 charset 时按 UTF-8 解码；
3. 不使用 Servlet API 历史默认的 `ISO-8859-1` 去解释 Jackson 实际输出的 UTF-8 JSON；
4. Schema V2 对历史已经落库、且可安全识别的 mojibake 做一次迁移修复。

这解决了监控详情中出现 `å¤§æ¨¡å`、`ææ°` 等典型 UTF-8→Latin-1 乱码的问题。

### 10.2 粗略容量估算

| 日请求量 | 平均 5 KB / 条 | 平均 20 KB / 条 |
|---:|---:|---:|
| 10,000 / 日 | ≈ 50 MB / 日 | ≈ 200 MB / 日 |
| 50,000 / 日 | ≈ 250 MB / 日 | ≈ 1 GB / 日 |
| 100,000 / 日 | ≈ 500 MB / 日 | ≈ 2 GB / 日 |

因此必须把 metadata retention 与 payload retention 分开。

# 第三部分：容器销毁重建与丝滑升级设计

## 11. 核心原则：容器是一次性的，数据目录不是

OpenReach 后续升级很可能是：

```text
docker pull 新镜像
      ↓
docker rm -f 旧容器
      ↓
重新创建新容器
```

因此绝对不能把 SQLite DB 写进容器可写层。

### 11.1 推荐宿主机目录

单机部署建议固定一个状态根目录：

```text
/data/openreach/
├── data/
│   └── monitor/
│       ├── openreach-monitor.db
│       ├── openreach-monitor.db-wal
│       ├── openreach-monitor.db-shm
│       └── backup/
└── logs/
```

容器内部：

```text
/app/data   ← 宿主机 /data/openreach/data
/app/logs   ← 宿主机 /data/openreach/logs
```

这样镜像和数据生命周期彻底分离：

```text
Image      可以随时替换
Container  可以随时销毁
Data       始终由宿主机保留
Logs       始终由宿主机保留
```

### 11.2 推荐 Docker 形态

v0.1.3 已真实接入 SQLite，Docker Run 推荐：

```bash
sudo mkdir -p /data/openreach/data /data/openreach/logs
sudo chown -R 10001:10001 /data/openreach

docker run -d \
  --name openreach \
  --restart unless-stopped \
  -p 8080:8080 \
  -e OPENREACH_MONITOR_DATA_DIR=/app/data/monitor \
  -e OPENREACH_LOG_PATH=/app/logs \
  -v /data/openreach/data:/app/data \
  -v /data/openreach/logs:/app/logs \
  codercl/openreach:<version>
```

Compose 推荐：

```yaml
services:
  openreach:
    volumes:
      - "${OPENREACH_DATA_DIR:-./data}:/app/data"
      - "${OPENREACH_LOG_DIR:-./logs}:/app/logs"
```

> v0.1.3 已正式使用该目录契约。第一次产生真实 API 调用后，SQLite 会在 `/app/data/monitor/` 下持续保存请求元数据与 Payload；销毁容器不会删除宿主机 `data` 目录。

## 12. 为什么推荐显式 Host Bind，而不是只依赖 Docker Named Volume

Named Volume 本身也能在删除容器后保留数据，但 OpenReach 是面向自部署用户的开源项目，默认使用显式宿主机目录更容易：

- 直接知道数据在哪里；
- 容易做 rsync / tar / 磁盘快照；
- 迁服务器时直接复制 `/data/openreach/data`；
- 排障时无需先查 Docker volume 名称；
- 用户不会因为误执行 `docker compose down -v` 把 Named Volume 一并删掉。

因此推荐：

```text
默认：Host Bind
可选：Docker Named Volume
```

如果用户使用 NAS / NFS，只能把**备份文件**同步过去，不建议把运行中的 SQLite WAL 数据目录直接作为跨主机共享目录。

---

## 13. 容器权限与 read_only 模式

当前镜像运行用户是：

```text
UID/GID = 10001:10001
```

同时根文件系统使用 `read_only: true`。

因此真实接入 SQLite 时：

1. Dockerfile 创建 `/app/data`；
2. `/app/data` 属主设为 `10001:10001`；
3. Compose / Docker Run 将宿主机 data 目录挂载到 `/app/data`；
4. 只允许 `/app/data`、`/app/logs`、`/tmp` 等明确目录可写；
5. 不为了 SQLite 关闭整个容器的 `read_only` 安全策略。

Linux Host Bind 需要确保宿主机目录对 UID 10001 可写。v0.1.3 的 `docker-compose.yml` 已加入一次性 `openreach-init`：它只以 root + `CAP_CHOWN` 创建/修正 `/app/data` 与 `/app/logs` 权限，完成后退出；正式 `openreach` 服务仍保持 UID 10001、`read_only: true`、`cap_drop: ALL`。因此标准 `docker compose up -d` 不需要用户手工 chown。

## 14. 数据库 Schema 与 OpenReach 版本必须解耦

不要写成：

```text
OpenReach v0.1.4 = DB v0.1.4
```

应该独立维护：

```text
OpenReach App Version: 0.1.4
Monitor Schema Version: V3
SQLite Engine Version: 3.x
```

三者分别升级。

建议 migration：

```text
src/main/resources/db/monitor/
├── sqlite/
│   ├── V001__init.sql
│   └── V002__future_change.sql
├── mysql/                 # 后续新增 MonitorRecordStore 时加入
│   ├── V001__init.sql
│   └── V002__future_change.sql
└── postgresql/            # 后续新增 MonitorRecordStore 时加入
    ├── V001__init.sql
    └── V002__future_change.sql
```

即使用户从 v0.1.3 直接跳到 v0.1.8，也由 Migration Engine 依次执行 V1 → V2 → ... → Vn，而不是要求用户逐个安装 OpenReach 中间版本。

## 15. 新容器启动时的自动升级流程

推荐启动顺序：

```text
新容器启动
   │
   ▼
检查 /app/data/monitor
   │
   ├── DB 不存在 → 创建新 DB + 执行全部 migration
   │
   └── DB 已存在
          │
          ▼
      PRAGMA quick_check（已实现）
          │
          ▼
      读取 monitor_schema_version
          │
          ├── 已是最新 → 直接启动 Monitor
          │
          └── 有待执行 migration
                  │
                  ▼
              VACUUM INTO 创建一致性升级前快照
                  │
                  ▼
              按 Schema Version 顺序执行 migration
                  │
                  ▼
              再次 quick_check
                  │
                  ▼
              启动 Monitor Writer / API
```

### 15.1 migration 失败怎么办

原则仍然是：

> Monitor 不能拖垮 OpenReach 核心 Search 能力。

如果监控 DB 升级失败：

- Monitor Storage 标记为 `DEGRADED / UNAVAILABLE`；
- 停止真实监控写入，避免继续破坏 DB；
- `/monitor` 明确提示存储升级失败；
- Search / Image Search / Read 仍可以继续服务；
- 日志输出 DB path、schema version、migration error 和可恢复 backup；
- 不静默吞异常，也不自动删除旧 DB。

## 16. 升级前自动备份

### 16.1 不能只复制一个 `.db`

WAL 模式运行时可能同时存在：

```text
openreach-monitor.db
openreach-monitor.db-wal
openreach-monitor.db-shm
```

因此不能在数据库在线写入时只 `cp openreach-monitor.db` 就宣称完成一致性备份。

v0.1.3 已预置升级前一致性快照流程：当“已有 DB Schema < 当前程序支持 Schema”时，先通过 SQLite `VACUUM INTO` 生成独立快照到：

```text
/app/data/monitor/backup/
```

示例：

```text
openreach-monitor-before-schema-V4-20260816T150000.db
```

只在存在待执行 migration 时做“升级前强制快照”，默认保留最近 5 个升级快照，可通过 `OPENREACH_MONITOR_BACKUP_RETENTION_COUNT` 调整。

## 18. 回滚设计

数据库 migration 只做 forward，不维护自动 down migration。

假设：

```text
旧镜像 v0.1.4 + Schema V3
      ↓ upgrade
新镜像 v0.1.5 + Schema V4
```

如果新版本需要回滚：

```text
停止新容器
   ↓
恢复升级前自动生成的 V3 SQLite 快照
   ↓
重新启动 v0.1.4 镜像
```

不要让旧版本应用直接读取比它更新的 Schema 并“猜着运行”。

---

## 19. SQLite Engine 自身升级

OpenReach Schema Migration 与 `sqlite-jdbc` / SQLite Engine 升级是两件事。

升级 SQLite JDBC 版本前必须准备旧版本真实 fixture DB，并验证：

1. 新 JDBC 可以打开旧 DB；
2. migration validate / migrate 正常；
3. overview 查询正常；
4. records / detail 查询正常；
5. `PRAGMA quick_check` 正常；
6. 模拟进程 kill 后重新启动能恢复；
7. 旧数据没有乱码 / 时间偏移 / payload 破坏。

---

## 20. SQLite 参数建议

```sql
PRAGMA journal_mode=WAL;
PRAGMA synchronous=NORMAL;
PRAGMA foreign_keys=ON;
PRAGMA busy_timeout=5000;
```

监控数据属于可重新产生但又希望尽量保留的运维数据，因此 `NORMAL` 是性能与可靠性的合理默认值；如果部署方更强调掉电耐久性，可以提供配置切换到 `FULL`。

## 21. 总览查询与后续汇总表

### 21.1 初版直接查明细

```sql
SELECT
    COUNT(*) AS total,
    SUM(CASE WHEN success = 1 THEN 1 ELSE 0 END) AS success_count,
    SUM(CASE WHEN success = 0 THEN 1 ELSE 0 END) AS failure_count,
    COUNT(DISTINCT NULLIF(TRIM(client_ip), '')) AS unique_ip_count,
    AVG(latency_ms) AS avg_latency
FROM monitor_request_record
WHERE request_time_ms >= ?
  AND request_time_ms < ?;
```

失败下钻：

```sql
SELECT ...
FROM monitor_request_record
WHERE request_time_ms >= ?
  AND request_time_ms < ?
  AND success = 0
ORDER BY request_time_ms DESC
LIMIT ? OFFSET ?;
```

### 21.2 数据规模上来后再增加汇总表

```text
monitor_daily_stat
```

按日期 + endpoint 存。需要注意：**独立 IP 数不能简单把每日 `unique_ip_count` 相加**，因为同一客户端可能跨日重复。自定义日期范围仍应从明细表执行 `COUNT(DISTINCT client_ip)` 精确统计；只有后续数据规模明显增大时，再考虑专门的 distinct sketch / 预聚合方案。

- total；
- success；
- failure；
- total_latency；
- latency buckets / p95 snapshot。

不要在请求量还没证明有必要时就引入复杂 OLAP 架构。

## 22. 存储接口从第一版隔离（已落地）

```java
public interface MonitorRecordStore {
    void initialize() throws Exception;
    void saveBatch(List<MonitorRequestEvent> events) throws Exception;
    MonitorOverview overview(long startTimeMs, long endTimeMs, long droppedEvents) throws Exception;
    List<MonitorTrendPoint> trend(long startTimeMs, long endTimeMs, String bucket, int timezoneOffsetMinutes) throws Exception;
    List<MonitorEndpointStat> distribution(long startTimeMs, long endTimeMs) throws Exception;
    MonitorRecordPage query(MonitorRecordQuery query) throws Exception;
    Optional<MonitorRecordDetail> findByTraceId(String traceId) throws Exception;
    long streamDetails(MonitorRecordQuery query, MonitorRecordSink sink) throws Exception;
    int deletePayloadBefore(long cutoffTimeMs) throws Exception;
    int deleteRecordsBefore(long cutoffTimeMs) throws Exception;
}
```

实现：

```text
SqliteMonitorRecordStore        # v0.1.3 已实现
MysqlMonitorRecordStore         # 后续扩展
PostgresMonitorRecordStore      # 后续扩展
```

配置：

```yaml
openreach:
  web:
    monitor:
      storage: sqlite   # v0.1.3 实现 sqlite；mysql/postgresql 为后续 Store 扩展目标
```

SQLite Schema 第一版应避免绑定私有能力：

- 时间统一 epoch ms；
- JSON payload 初期使用 TEXT；
- 不依赖 `rowid` 作为业务 ID；
- `trace_id` 作为跨库稳定逻辑标识；
- SQL 全部收敛在对应 `MonitorRecordStore` 实现内部；
- Controller / Service 不感知具体存储引擎。

---

## 23. 什么时候升级 MySQL / PostgreSQL

出现以下明显信号之一时进入服务型数据库评估：

1. OpenReach 开始多实例部署，需要多个 JVM / 主机同时写；
2. SQLite writer queue 长时间堆积；
3. 持续出现 `SQLITE_BUSY`，短事务、batch、busy timeout 后仍无法解决；
4. 监控库进入几十 GB 以上且长周期复杂统计频繁；
5. 需要集中式备份、HA、远程托管数据库；
6. 需要多个 OpenReach 节点统一监控。

在这些条件出现之前，SQLite 更符合 OpenReach 的产品定位。

---

## 24. SQLite → MySQL / PostgreSQL 数据迁移

未来可提供：

```bash
java -jar openreach.jar monitor migrate \
  --from sqlite:/app/data/monitor/openreach-monitor.db \
  --to mysql://...        # 或 postgresql://...
```

迁移流程：

```text
SQLite 一致性 snapshot
   ↓
按 id / request_time_ms 分批读取
   ↓
MySQL batch insert / PostgreSQL COPY
   ↓
总 count 校验
   ↓
成功/失败 count 校验
   ↓
trace_id 抽样校验
   ↓
切换 storage=mysql / postgresql
```

迁移过程保持 SQLite 原库不删除，直到新库验收完成。

## 29. v0.1.3 最终决策

当前版本的正式方向收敛为：

```text
Monitor UI
  ├── 独立 /monitor
  ├── 服务端登录
  ├── 今日 / 7 日 / 自定义日期
  ├── 失败下钻
  └── 明细详情

Persistence（v0.1.3 已接入）
  ├── MonitorRecordStore SPI
  ├── SQLite + WAL
  ├── Async single writer
  ├── metadata / payload 分表
  ├── Schema Migration V2
  ├── /app/data
  ├── Host Bind /data/openreach/data
  ├── openreach-init 自动目录权限修正
  ├── 容器可销毁、数据不销毁
  ├── 升级前一致性快照框架
  ├── Forward Migration
  └── Future MySQL / PostgreSQL
```

最核心的部署约束只有一句：

> **OpenReach 的镜像和容器必须是可替换的，`/app/data` 才是真正需要跨版本长期保存的状态。**

因此从 v0.1.3 起，应把 `/app/data` 视为 OpenReach 的稳定持久化契约；升级只换镜像 / 容器，不换 data 目录。
